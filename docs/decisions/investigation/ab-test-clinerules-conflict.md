## ⚠️ 统计局限声明（必读）

**本实验 n=3，不足以区分 A vs B 的 cell 间差异。**

- A-prefix `[2,0,2]` 和 B-prefix `[1,2,1]` **总数都是 4**。它们的"工具调用率"差异（67% vs 100%）**完全来自 A 的单次 0 运行**。把那个 0 换成 1，裁决就翻转。
- A+prefix 仅 1 次运行，**不应进对比表**。
- 唯一被数据稳稳支撑的结论：**加前缀（B-prefix → B+prefix）将工具调用从 [1,2,1]=4 压到 [0,0,1]=1**。下降幅度大、方向一致，可信。
- 其余所有 cell 间高下都在 ±1 次的噪声里，**不据此做架构决策**。

## 一、测试动机

### 1.1 原始假说

第二轮源码探查结论为"registerRule 在 section 10（末尾追加），模型对 section 1-7 有位置+服从惯性"。
由此推导出 P0 改进："将 constitution 从 section 10 搬到 section 8（.clinerules 胖入口化）"。

### 1.2 外部评审第一轮质疑

1. **位置假说最脆**：LLM 注意力分布有 primacy + recency 双峰，section 10 未必是"最差"
2. **"DO NOT RE-READ" 前缀有效本身就是反证**：如果 section 10 真是服从洼地，一个前缀不该救得回来
3. **真实机制可能是"冲突+歧义"**
4. **建议 A/B 差分测试**：隔离"冲突"变量

### 1.3 外部评审第二轮纠偏

测试完成后，评审指出：

1. **样本量不足**：n=3 无法区分 A vs B，唯一稳的是"前缀有效"
2. **"冲突消除反而更差"是过度解读**：B 的条件语言没有消除读文件指令，只是把它包进了条件——条件分支对模型是一个"可以合理化的出口"
3. **真实框架**：决定行为的不是"有无冲突"，而是"**读文件表述的可触发强度**"
4. **前缀是唯一被验证的杠杆**，应从 P2 升为 P0；胖入口降级为纯工程改进
5. **建议两个下一步实验**：prefix 分解 + 冗余/合理工具调用标签

## 四、假说验证结论

### 4.1 位置假说：❌ 不成立

registerRule 在所有变体中都位于 section 10，但行为差异巨大（0 到 4 次工具调用）。位置不是决定性因素。

### 4.2 冲突假说：⚠️ 无法验证

~~"冲突消除（变体 B）反而比有冲突（变体 A）表现更差"~~——**此结论撤回**。

A-prefix `[2,0,2]=4` 和 B-prefix `[1,2,1]=4` 总数相同。差异（67% vs 100%）完全来自 A 的单次 0 运行。**在 n=3 下无法区分这是真效应还是噪声。**

更重要的修正：变体 B 的条件语言**并没有真正消除读文件表述**——"若未出现注入段，手动读 HANDOFF.md"仍然包含一条可触发的读路径。所以"冲突消除"这个变量根本没有被干净地隔离。

### 4.3 指令强度假说：✅ 成立，且 Round 2 揭示了更精细的机制

**Round 1（n=3）**：
- B-prefix（无前缀）：`[1,2,1]` = 4 次工具调用
- B+prefix（有前缀）：`[0,0,1]` = 1 次工具调用

**Round 2（n=10）进一步分解前缀组件**：见 §六。

### 4.4 问题复杂度假说：✅ 成立

简单问题全通过（0 工具调用），复杂问题分化显著（1-4 次工具调用）。问题复杂度是最强分隔变量。

### 4.5 修正后的框架：读文件表述的可触发强度

**决定模型行为的不是"有无冲突"或"位置优劣"，而是"读文件表述的可触发强度"**：

| 表述类型 | 示例 | 可触发强度 | 模型行为 |
|---------|------|-----------|---------|
| 硬指令 | "必须读 constitution.md" | 高 | 模型执行读取 |
| 软条件 | "若未出现注入段，手动读" | 中 | 模型可能合理化触发 |
| 强否定 | "DO NOT RE-READ FILES" | 压制 | 模型抑制读取冲动 |

B+prefix 最优，正是因为它**同时**有条件语言（fallback）+ 强否定前缀（压制软条件的触发路径）。前缀把条件里那条软读路径也盖住了。

### 6.4 核心发现：协同效应，非主效应

**回答评审问题"前缀的哪一部分在起作用"**：

> ** neither alone does the work. The combination creates a synergistic effect.**

| 组件 | 单独效果 | 合并效果 |
|------|---------|---------|
| 事实陈述（"内容已自动加载"）| 100% 工具调用率 | — |
| 否定祈使（"DO NOT RE-READ"）| 100% 工具调用率 | — |
| **两者组合** | — | **20% 工具调用率** |

这不是加性效应（100% + 100% → 50%），而是**相变效应**（100% + 100% → 20%）。两个组件单独都完全无效，组合后效果跃升。

**机制假说**：
- 事实陈述 alone → 模型知道内容在那里，但不确定是否"够用" → 仍验证
- 否定祈使 alone → 模型被禁止读，但不信任内容完整性 → 仍读（违反指令）
- **两者组合** → 模型知道内容在那里 + 被明确告知不要验证 → 信任建立，停止读取

### 6.5 冗余/合理标签结论

**回答评审问题"残留的工具调用是真该调用还是浪费"**：

R2-A3 的 2 次有工具调用的运行：
- **Run 2**：3 冗余读 + 6 合理读 → **混合调用**（读了注入段内的 constitution/rules，也读了注入段外的 examples/hooks）
- **Run 10**：0 冗余读 + 0 合理读 → 工具调用是 search（非 file read），路径未被捕获

**结论**：
- 冗余读率 = 1/10 = **10%**（仅 Run 2 有冗余读）
- 合理读率 = 1/10 = **10%**（仅 Run 2 有合理读）
- **Round 1 的 33% 是小样本高估**，n=10 后实际为 10-20%
- Run 2 的合理读（6 次）表明模型确实在读注入段外的内容（examples/ 等），这些是**合理验证**
- **不应继续把 10% 往 0 压**——Run 2 的混合调用表明模型在做合理的跨文件追踪，只是同时夹带了一些冗余读
