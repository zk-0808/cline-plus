# 通用化 Rubric — 判定动作 vs 项目取值分离清单

> **生命周期**：版本绑定 — v1.0 框架定型后归档，后续变更走 ADR。
>
> **身份**：GV-1 产出。本文档是 Core Constitution 与 examples/ 通用化蒸馏的判定工具——回答"哪些该留、哪些该去"。
>
> **使用场景**：① 写 core/constitution.md 时按本 rubric 删除项目取值；② EX-1b/EX-2/EX-3 通用化时照本 rubric 蒸馏；③ 第二个项目接入时按本 rubric 修改 examples/。

---

## 一、核心判定原则

> 一条规则 = **判定动作**（保留）+ **项目取值**（去除）。
>
> - **判定动作**：何时检查 / 检查什么 / 违规怎么办——跨项目通用的"动词+对象类型"
> - **项目取值**：具体阈值 / 路径 / 工具名 / 版本号 / 字段名——随项目而变的"参数"

---

## 二、五维判定清单

每条规则按下列五维拆解。判定动作留下,项目取值替换为占位符或移到假设清单。

### 维度 1：触发条件（when）

| 类型 | 内容 |
|------|------|
| **判定动作** | 触发条件的事件类型（用户指令 / 文件状态 / 时间间隔 / 版本变化 / 错误信号）|
| **项目取值** | 具体阈值（如"≥5 个文件"中的 5）、具体时间间隔（如"6 个月"中的 6）|

**蒸馏动作**：保留事件类型枚举,具体数值移到 constitution 的"项目可调参数"区或假设清单。

### 维度 2：执行门控（what to check）

| 类型 | 内容 |
|------|------|
| **判定动作** | 检查的对象类型（文件存在性 / API 契约 / 证据类型 / 工作目录状态）|
| **项目取值** | 具体字段名（如 `cline --version`）、具体路径（如 `.vscode/extensions/`）|

**蒸馏动作**：保留对象类型抽象,具体路径/字段名移到假设清单。

### 维度 3：失败动作（on fail）

| 类型 | 内容 |
|------|------|
| **判定动作** | 违规时的动作类型（停止 / 回滚 / 降级 / 登记 / 提议）|
| **项目取值** | 具体降级目标（如"降为 Hypothesis"）、具体登记位置（如某个 Registry 文件）|

**蒸馏动作**：保留动作类型语义,具体目标位置移到 rules/ 薄入口（项目级可填）。

### 维度 4：证据类型（evidence types）

| 类型 | 内容 |
|------|------|
| **判定动作** | 可接受的证据类型枚举（官方文档 / 源码 / 实测 / Example / 第三方报告）|
| **项目取值** | 具体证据来源（如某 GitHub issue 编号、某 PR 链接、某文件路径）|

**蒸馏动作**：保留证据类型层级（官方 > 源码 > 实测 > 推断），具体来源移到 ADR 的 `evidence_as_of` 字段。

### 维度 5：沉淀位置（where to sediment）

| 类型 | 内容 |
|------|------|
| **判定动作** | 规则归属层（core / rules / examples / capability / hook）|
| **项目取值** | 具体目录路径（如 `docs/plugin/project-rules.md`）|

**蒸馏动作**：保留层级语义,具体路径由框架目录结构（GV-7 §三）映射。

## 三、通用化检查清单（EX-* 蒸馏用）

每条规则蒸馏后,逐项检查:

- [ ] **工具名/版本号**：是否含具体工具名（如 "Cline" / "PowerShell"）→ 移到假设清单
- [ ] **项目特定阈值**：是否含硬编码数值（如 "≥5 文件" / "6 个月"）→ 参数化为 `<N>` / `<interval>` 或移到 constitution 的"项目可调参数"区
- [ ] **项目特定路径**：是否含 cline++ 路径（如 `docs/plugin/` / `context-snapshot/`）→ 替换为框架相对路径（`.governance/...`）或移到假设清单
- [ ] **项目特定概念**：是否含 cline++ 特有概念（codec bug / 提取器 / Loop Guard / V6 等）→ 移到假设清单或删除（不通用）
- [ ] **判定动作独立性**：去掉项目取值后,判定动作是否仍可独立执行？否 → 降级为 example 而非 rule
- [ ] **事故源由通用性**：规则源由的事故是否跨项目可复用？否 → 留 example 不入 constitution

## 四、假设清单格式（每个 example 文件头部强制）

```markdown
## cline++ 特定假设

> 本示例包从 cline++ 项目蒸馏。下列假设若不适用你的项目,需修改对应章节。

| 假设 | 影响章节 | 修改建议 |
|------|---------|---------|
| 假设存在 Cline CLI 工具链 | §1 / §3 | 改为你的 agent CLI |
| 假设 Windows + PowerShell 5.x 环境 | §1.4 / §1.6 | 改为你的 shell |
| 假设存在 codec bug 阻塞场景 | §3.3 特化字段 | 删除该字段 |
| ... | ... | ... |
```

**填写约束**:
- 每个 example 文件**必须**含此区块（GV-7 §三 examples/ 假设清单强制）
- 假设项**必须**指向具体章节,便于用户定位修改
- "修改建议"**必须**可执行（不能写"按需调整"）

---

## 五、rubric 自身的复查触发

- **触发条件**：第二个项目 dogfood 接入时,若发现本 rubric 五维不足以判定某条规则的通用性 → 补维度
- **失效信号**：若连续 3 条规则无法用本 rubric 五维拆解 → rubric 设计有缺陷,需重构
